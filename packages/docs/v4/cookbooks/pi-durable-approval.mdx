## When to use this

Use this when a browser job must wait for a human decision across process restarts. Pi Durable stores the conversation and application documents; durable-harness supplies local Workflow World storage. The human submits the order in Browserbase Live View.

| Browser | Language | Output |
| --- | --- | --- |
| Browserbase | TypeScript | Persisted proposal and approval; verified `status.json` |

## Goal and output

Fill the [httpbin test order form](https://httpbin.org/forms/post), save its actual values and keep the CLI open at an approval prompt. Reopen the same run, approve those values, submit through Live View and return control. Pi checks that the echoed response matches the saved order. No payment is made.

## Prerequisites and inputs

Use Node.js 24.18+ and pnpm. Add `BROWSERBASE_API_KEY` and `OPENAI_API_KEY` to `.env`. OpenAI powers Pi; deterministic Stagehand browser operations need no separate browser model. The form uses demonstration customer data.

Pi Durable is experimental. This recipe pins Pi Durable `1.4.0` and `durable-harness@0.0.1-beta.6`. See the [version notes](/v4/cookbooks/overview#durable-dependency-versions).

## Check out and run

Source: [`packages/examples/cookbooks/pi-durable-approval`](https://github.com/browserbase/stagehand/tree/main/packages/examples/cookbooks/pi-durable-approval). Use the [sparse checkout instructions](/v4/cookbooks/overview#run-a-cookbook), then:

```bash
cd packages/examples/cookbooks/pi-durable-approval/typescript
cp .env.example .env
pnpm install --frozen-lockfile
# Fill in .env before starting.
pnpm start
```

The CLI prints the proposal, decision ID and Live View URL, then waits for input in the same terminal:

```bash
# At the terminal prompt, type: approve
# Submit the approved form yourself in Live View.
# Back at the terminal prompt, type: done
# The agent verifies the response, then exits.
pnpm start cleanup
```

At the approval prompt, type `reject` to stop without submitting. Type `pause` or press Ctrl+C while waiting to leave the decision saved; `pnpm start resume` reopens it. Scripted commands `approve <decision-id>`, `return <decision-id>` and `reject <decision-id>` remain available when the CLI is not already running.

## How the job works

### Reopen the agent's storage

`src/index.ts` connects the native Pi harness to a local World. The same saved storage ID reopens the conversation on the next CLI invocation:

```typescript
const open = resumeWith(async (storage) => {
  return (await openAgent(storage)).harness;
}, { world, name: "order-approval" });

const lease = await acquireHarness(await savedId(), open, {
  world,
  name: "order-approval",
});
```

This excerpt shows the storage boundary. The runnable CLI also registers the queue, retains the browser and document handles, and releases the lease in `finally`.

### Save the proposal, then check approval

`prepare_order` fills the form with Stagehand locators and saves its actual values in a Pi document. The pending decision ends the turn. The approval handler reads the form again before committing consent:

```typescript
const actual = await browser.formValues();
await store.update((draft) => {
  approveOrder(draft, decisionId!, actual);
});
```

`approveOrder` requires the same decision ID and a matching fingerprint of every form value. Approval alone does not click Submit.

### Verify after human return

The human submits in Live View and types `done` at the waiting terminal. Pi's `verify_order` tool compares httpbin's echoed response with the approved values:

```typescript
await browser.confirmation(state.decision.values);
await store.update((draft) => {
  draft.confirmed = true;
});
```

A mismatch throws before `confirmed` can become true. The CLI's stable initial and return request IDs prevent duplicate input submissions after a restart.

## Expected result and manual checks

`STATE_DIR` defaults to `out/run`. It contains the local World, `run.json` and `status.json`. The final status must contain `confirmed: true`; a human return is not proof of success.

Before a PR, manually verify:

1. Start a run, type `pause` at approval, then run `status` and `resume`. The browser session, decision ID and proposal must be unchanged.
2. Change a field in Live View. Typing `approve` must refuse it and keep the prompt open. Restore the saved value, type `approve`, submit in Live View and type `done`; expect a matching confirmation.
3. Use a fresh `STATE_DIR` to test rejection. It must not submit or become approved later.

Run `pnpm typecheck` to check the source types. Use the steps above to verify the browser flow and restart behavior.

## Session lifetime and recovery

The browser is a 30-minute keep-alive session, including human waiting time. Durable agent state can outlive that browser. If it expires, retain the history, start a fresh task with a new `STATE_DIR`, and approve fresh values. A crash between browser allocation and saving its ID can leave a session until its timeout.

Run one CLI process per state directory. While its terminal prompt is active, use that prompt rather than starting another command against the same directory. After a hard crash, the lock expires after 30 seconds. The next command waits up to 35 seconds for it to clear; it does not require you to delete a lock or retry commands manually. Keep the same directory and dependency pins when resuming. `cleanup` releases the browser and retains history. Live View URLs grant interactive access and are printed locally.

This CLI resumes when invoked; it does not run an unattended worker. See [storage and hosting](/v4/cookbooks/overview#durable-storage-and-hosting) before deploying it.
