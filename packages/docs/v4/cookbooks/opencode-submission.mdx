## Follow the code

1. `src/index.ts` creates OpenCode through `durable-harness/opencode` and persists application state in a World document.
2. `src/state.ts` checks approval and exact form values. The submission tool commits `attempted = true` before clicking.
3. `CRASH_AFTER_SUBMIT=1` stops the process after the click but before its tool result is saved.
4. On resume, the CLI sees `attempted` and verifies the current response directly, without asking the model to submit again.

The marker is conservative. A crash between saving it and clicking leaves an uncertain outcome even if nothing was submitted. httpbin does not offer a transaction lookup or idempotency key, so the cookbook stops for manual review. A real service with those APIs can support stronger reconciliation.

## When durability helps

OpenCode runs its agent loop inside durable-harness. Its events and tool results are stored in a local World. The model gets only `prepare_request`, `submit_request` and `verify_request`; it has no general browser or shell tool that could bypass the submission guard.

The prepared request includes a reference in its comments. The approval is tied to the exact form values. Before clicking Submit, the tool commits an `attempted` marker through the session document API. That write intentionally precedes the external effect. A crash after the marker but before the click can therefore leave an unsubmitted request marked uncertain. Recovery checks the page; it does not authorize another attempt.

`CRASH_AFTER_SUBMIT=1` kills the process after the click but before the tool returns. Unset it, wait for the stale CLI lock to clear, and resume. A matching httpbin response confirms success. An expired browser, missing confirmation, or mismatched response stops with an error and requires manual review. httpbin is an echo service, not an idempotent transaction system. This example does not promise exactly-once website actions.

Keep OpenCode's packages pinned to `2.0.22`, the version this durable-harness beta supports. The latest OpenCode release may be incompatible.

## Run

Source: [`packages/examples/cookbooks/opencode-submission`](https://github.com/browserbase/stagehand/tree/main/packages/examples/cookbooks/opencode-submission). Use the [sparse checkout instructions](/v4/cookbooks/overview#run-a-cookbook).

```bash
cd packages/examples/cookbooks/opencode-submission/typescript
cp .env.example .env
pnpm install --frozen-lockfile
```

Fill in `.env`, then:

```bash
pnpm start
# Review the saved values and Live View before approving.
pnpm start approve <decision-id>
# After a crash, unset CRASH_AFTER_SUBMIT, then:
pnpm start resume
```

Use Node.js 24.18+. `BROWSERBASE_API_KEY` and `AI_GATEWAY_API_KEY` are required. The gateway key powers OpenCode. Deterministic Stagehand browser operations need no separate OpenAI key or browser model. Keys and account information belong in `.env`, which is ignored by Git.

## Browser operations

OpenCode gets three task-specific tools. Stagehand locators prepare and submit the form. The submission tool checks approval and commits an attempt marker before clicking. Recovery parses the confirmation and compares every field against the saved request.

Use the printed Browserbase session link to inspect execution and Live View for human interaction. These recipes use task-specific tools and DOM-based completion checks. Screenshots are optional visual evidence; they do not replace persisted decisions or confirmation checks.

## Expected output and checks

The CLI saves run identity and application output under `STATE_DIR`, default `out/run`. This recipe saves `status.json` with its browser binding, decision and confirmation state. Pending decisions include their ID and reason. A human return is not proof that login or submission succeeded; the recipe must verify its completion condition. `status` does not launch a model turn. It refreshes the active-page Live View link when handoff is pending.

Run `pnpm typecheck` and `pnpm test`. The tests reopen a real local World with a stub harness and check persistence of the pre-submit marker and exact-value approval. They do not boot the OpenCode model or exercise its live tool loop. Live browser behavior and model execution remain untested. `pnpm start cleanup` releases the remote browser, while preserving agent history.

## Manual browser check

Prepare the request, then set `CRASH_AFTER_SUBMIT=1` for the approval command. After the intentional crash, unset it and wait 30 seconds for the lock to expire. Resume with the same `STATE_DIR`. Expect confirmation recovery without another click. If the confirmation is missing, expect an unknown outcome, not a retry.

These live steps remain untested.

## Session lifetime and recovery

These durable recipes use a 30-minute Browserbase keep-alive session, including human waiting time. The plan must support keep-alive. The decision can survive longer than that browser; its tab, OTP and external website state cannot. If reconnect fails, stop and start a fresh task with a new `STATE_DIR`. A pending approval or uncertain submission must not be silently applied to a replacement browser.

Keep the same state directory, inputs and dependency pins when resuming. Run one CLI process per directory. After a hard crash, its lock expires after 30 seconds. Live View links grant browser control and are printed only in the local terminal. Release the browser after completion. A crash between allocating a browser and recording its ID can leave an orphan until its 30-minute timeout.

## Deploying beyond this CLI

This example resumes when you invoke the CLI again. It does not deploy a worker or keep processing after the local process exits. See [storage and deployment options](/v4/cookbooks/overview#durable-storage-and-hosting) for the distinction between durable state, a running worker and a live browser.
